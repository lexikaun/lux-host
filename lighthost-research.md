# A lightweight standalone replacement for LightHost

Revised November 22, 2026. The proposed product is a small Windows tray app that takes one selected input, runs an ordered effects chain, and sends the result to one selected output. Voicemeeter is a supported route alongside physical interfaces and installed virtual audio devices. The proposed improvements target easier routing, safe edits, predictable device recovery, and a small background footprint. The original research used source and documentation. Performance and compatibility still need live validation.

## What LightHost does today

- LightHost is a tray utility that puts a chain of plug-ins between a selected input and output. It can open plug-in editors, save plug-in state and order, and bypass and reorder effects. The Windows build configuration already enables VST2, VST3, WASAPI, ASIO, and DirectSound. The original repository's latest release is v1.2.1, published November 10, 2016. [Maintainer's feature list](https://github.com/opencma/LightHost/issues/1) · [Build configuration](https://github.com/opencma/LightHost/blob/03cb4d0d711b6a5789c295d770f9b7de363779b7/LightHost.jucer#L134-L138) · [Release record](https://api.github.com/repos/opencma/LightHost/releases/latest)
- Its graph wires only channel indices 0 and 1, even though its audio settings allow many device channels. Bypass and reorder clear and rebuild the chain, closing plug-in windows and creating new instances. The graph adds a direct path when the list is empty. With effects loaded and all bypassed, the source implies that nothing is wired to the output. Load also uses the plug-in instance without checking whether creation succeeded. These are findings from reading the source. [Graph and load path](https://github.com/opencma/LightHost/blob/03cb4d0d711b6a5789c295d770f9b7de363779b7/Source/IconMenu.cpp#L123-L176) · [Bypass and reorder](https://github.com/opencma/LightHost/blob/03cb4d0d711b6a5789c295d770f9b7de363779b7/Source/IconMenu.cpp#L388-L442) · [Device selector](https://github.com/opencma/LightHost/blob/03cb4d0d711b6a5789c295d770f9b7de363779b7/Source/IconMenu.cpp#L492-L511)
- Users have reported a silent Banana insert, a VST3 scan crash, lost or garbled settings on reorder, and a crash after removing a selected driver. The Banana thread describes a routing issue that also occurred with other hosts. These reports are leads for testing. [Banana insert report](https://github.com/opencma/LightHost/issues/44) · [VST3 scan report](https://github.com/opencma/LightHost/issues/48) · [State report](https://github.com/opencma/LightHost/issues/52) · [Driver report](https://github.com/opencma/LightHost/issues/63)

## Routing from the same device selector

`Selected input and channels → effects chain → selected output and channels`

- **Windows Audio (WASAPI shared).** Choose a capture endpoint and a playback endpoint. For a virtual microphone, route a USB mic through the host to **CABLE Input**, then select **CABLE Output** as the recording device in the receiving app. The same picker can route a supported physical input to speakers or a Voicemeeter playback input. An installed virtual cable or mixer supplies the virtual recording endpoint. [JUCE device setup](https://docs.juce.com/master/structjuce_1_1AudioDeviceManager_1_1AudioDeviceSetup.html) · [VB-CABLE](https://vb-audio.com/Cable/)
- **ASIO.** Select one driver and its input/output channels. With Voicemeeter Banana, choose **Voicemeeter Insert Virtual ASIO**, select the matching channel pair, and enable its Patch Insert return. The effects return to the same strip, which can then feed B1 or another Banana bus. Banana exposes 22 pre-fader insert channels to one client and offers pre- and post-FX insert positions. A physical ASIO interface uses the same driver and channel controls. [VB-Audio Insert guide](https://voicemeeter.com/user-guide-connect-audio-apps-to-the-voicemeeter-insert-driver/) · [Banana manual, pp. 17–18 and 81](https://vb-audio.com/Voicemeeter/VoicemeeterBanana_UserManual.pdf)

The first version targets one mono or stereo chain. WASAPI and ASIO are two ways to open that chain. Device and channel availability depend on the chosen backend and installed driver.

## Improvements to prioritize

| Improvement | Proposed behavior | Verify it with |
| --- | --- | --- |
| Know where audio stops | Put the selected devices and channels, input and output meters, and whole-chain bypass on one screen. Show the active sample rate, buffer size, and any device or plug-in errors. The meters describe the host's input and output. | Test the route without effects. Disconnect the input, stop a plug-in from passing signal, and check that the meters and status distinguish the cases. |
| Edit effects while live | Keep plug-in instances and their settings when toggling bypass or reordering. Use a short transition and account for plug-in delay where needed for a clean bypass. An empty or fully bypassed chain passes dry audio. | Reorder effects and bypass them all while audio is flowing. Check for setting changes, silence, and audible clicks. |
| Survive restarts and missing devices | Save the last working device pair, channels, and chain. Reopen the same route when devices return. For an explicitly selected endpoint, show a waiting state while it is missing. Offer manual device selection and preserve the saved chain. | Unplug the mic, restart Banana, and relaunch with the previously selected driver unavailable. Verify the correct device resumes and settings survive. |
| Contain scan and load failures | Scan in an on-demand helper process. Record which plug-in failed and allow a retry. If a plug-in cannot be loaded, preserve its settings and let the chain follow the configured bypass or mute behavior. | Force a scan failure with an active chain and restart with a missing plug-in. Test the two fallback settings and check that the remaining state can be restored. |

Keep the Windows x64 prototype to a native tray process, a device picker, one chain, and native VST3 editors. Default to a serial processing path and spawn the scanner only when needed. A scanner helper protects discovery. A plug-in crash during live processing still requires runtime isolation, which adds overhead and can add latency. Check the user's plug-in list before deciding whether VST2 compatibility is needed for the first release. [JUCE host example](https://github.com/juce-framework/JUCE/blob/master/extras/AudioPluginHost/Source/UI/MainHostWindow.cpp) · [Microsoft device recovery guidance](https://learn.microsoft.com/en-us/windows/win32/coreaudio/recovering-from-an-invalid-device-error)

## Benchmarks and first build

Start by getting dry audio through both a WASAPI mic-to-virtual-cable route and a Banana Insert ASIO route. Run a sustained WASAPI test with separate devices to catch clock drift or buffering problems. Add one known VST3 effect, then verify bypass, device reconnect, and chain persistence before expanding the feature set. Compare CPU and memory with the tray window closed, glitches and measured input-to-output latency at the same settings, and time to recover after a disconnection. [Microsoft low-latency audio guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)

Use original LightHost as the baseline for simplicity and Light Host Modern as a baseline for routing and diagnostics. Light Host Modern already offers a serial chain, profiles, meters, scan workers, and experimental per-plug-in runtime isolation. Its documented isolation adds two worker blocks per isolated effect. Elka remains a useful comparison for the Banana route.
